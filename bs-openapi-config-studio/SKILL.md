# BS OpenAPI Config Studio 配置包

仅在用户显式调用 `$bs-openapi-config-studio` 时使用。本 Skill 处理 Config Studio 的配置模型和交付闭环；真实数据库连接、查询和已授权 DML 按 `bs-database-query` 的连接定位与事务规则执行。

## 范围与前置确认

- Config Studio 导出的是 `org_id=-1` 的全局 OpenAPI 配置。不要把单位配置伪装为 Studio 导出能力，也不要把全局、运营单位和行业单位库混为同一安装目标。
- 开始前确认 Studio 地址、目标数据库方言和 schema profile、包类型（增量或全量）、目标数据库连接及 schema、待配置对象清单，以及最终 ZIP 的用户指定路径。不得从历史环境、库名或本机端口猜测这些值。
- 输出路径优先使用用户指定位置，其余交付与临时文件遵循当前工作区 `AGENTS.md` 的目录约定。使用 `.mixed/` 时定位到工作区根目录，聚合工作区使用聚合根目录并复用已有任务目录。临时文件仅保存脱敏材料。
- 写入 Studio、执行安装 SQL、删除既有配置、调用会产生业务副作用的下游接口，都需要用户在当前任务中明确授权。配置校验、包检查和只读预检不构成写入授权。
- 先检查当前工作区状态和已有目标配置。保留无关改动和未跟踪文件；不为全量包自动删除旧数据。

## 选择包类型与建立配置图

- **增量包**只包含本次新增或变更对象，安装时不得删除未涉及的已有配置。先核对业务键是否已存在；冲突时停止并说明应更新、复用还是另选标识。
- **全量包**用于一个明确的、已获授权清空的全局配置范围。先按实际业务键、路由和模板引用预检删除范围；清空后再次核对无残留，才允许安装。不得用全量包覆盖不在本次范围内的全局配置。
- 配置模型按实际需要使用 `templates`、`dictionaries`、`internalApis`、`externalApis`、`routes`、`transformRules`、`routeOrchestrations`。只保留有真实依赖的对象，不为凑全字段创建空对象。
- 为本项目对象分配稳定且唯一的 `clientId`；64 位 `recId`、数据库主键和接口 ID 始终按字符串处理，不能经过 JavaScript `Number`。
- 检查依赖关系：外部接口的模板引用、路由的内外部接口引用、转换规则的路由引用、字典父子引用及接口参数层级必须都能在同一配置或已核对的目标全局配置中解析。
- 内部接口的启用业务键 `businessTag + interfaceTag + status=1` 必须唯一；同一交付包内的接口、路由和转换规则数量要与需求清单一致。不得依赖运行时 `selectOne()` 从重复记录中“碰巧”选到一条。
- 模板配置遵循接口契约。可选项（例如 SQL Server TLS 协议）默认不设值；只有用户或目标环境明确要求时才配置。数组参数、日期格式、分页起点和 SQL 类型转换先按真实调用端、驱动和源库能力验证，不能把一次故障的临时写法泛化到所有接口。

## Studio 创建、校验与原生导出

1. 使用目标 Studio 的 API 创建项目：`POST /api/projects`，明确项目名、目标方言和 schema profile。
2. 使用 `PUT /api/projects/{projectId}/configuration` 写入完整配置图；保存后检查 Studio 返回结果和对象数量，不以 HTTP 2xx 代替模型正确性。
3. 调用 `POST /api/projects/{projectId}/validate`。只有结果明确为 `valid=true` 才可导出；修复配置而不是手改导出 SQL。
4. 调用 `POST /api/projects/{projectId}/publication/verify` 记录安装前状态。首次安装时它可能因目标库尚未包含本包记录而显示前置条件未满足；这不是配置校验成功，也不能被报告为安装成功。
5. 通过 `GET /api/projects/{projectId}/sql/export` 下载 ZIP。ZIP 是 Studio 原始产物，不得修改 `manifest.json`、README、安装/校验 SQL、`api-model.json` 或 checksum。
6. 解压到用户指定的临时位置校验 `checksum.sha256`，并比对 `manifest.json`、`api-model.json` 与需求清单中的模板、接口、路由和转换规则数量。包内文件清单随 Studio 版本变化，以 manifest 和 checksum 为准；缺少安装或验证 SQL 时停止，不自行补写替代包。

## 经授权安装与配置核验

安装前先按 `bs-database-query` 核对“运行环境 → 数据源 → 连接别名 → 当前 schema → 配置表归属”。连接名已明确时仍须验证 schema 与目标表。

1. 执行包内 `00_precheck.sql`，人工核对冲突、目标范围和已有引用是否符合本次增量或全量设计。冲突、范围不明或模板引用异常时停止，不能直接安装。
2. 经明确安装授权后，以同一 stdin 会话和事务执行 `10_install.sql`；使用 `usql -X -w -q -v ON_ERROR_STOP=1 -1 <connection> < 10_install.sql` 的等价形式。禁止使用已知事务不可靠的 `usql -1 -f`，也不要自动执行 `99_rollback.sql`。
3. 执行 `90_verify.sql`，再直接核对模板、内部接口与参数、外部接口与参数、路由和转换规则的数量、`status`、`org_id=-1` 与业务键唯一性。验证失败先查实际已生效范围；仅在确认发生部分写入且用户授权后，才讨论针对性处理。
4. 再执行 Studio publication verify。只有它、包内验证和直接数据库核对均符合预期时，才报告数据库安装完成。

删除已安装配置不是安装步骤的一部分。用户明确要求删除时，先只读列出每个数据库、全局/单位范围、业务键和关联对象；未经精确范围确认，不执行 DELETE 或 rollback。

## 接口与下游 E2E

- 分别报告 Studio 配置校验、数据库安装核验、查询接口 E2E、下游业务 E2E；前一层成功不能替代后一层。
- 通过用户指定的网关或真实测试调用方验证接口路径、认证上下文、参数绑定和响应契约。需要源库比对时，使用等价 SQL 对比结果集合，并将 ID 按字符串比较。
- 对查询接口按契约覆盖常规数据、首/末/越界分页、空结果、日期边界与总数；对数组、枚举和 TLS 等特殊参数增加实际有效及异常场景。不要把某个业务的日期格式、页码或字段名当作所有接口的默认约定。
- 下游开具、写入或其他副作用调用必须逐项获得授权；默认使用最小抽样，记录脱敏请求要点、响应和可复查的结果查询，不批量执行。

## 交付

- 交付物是经完整性校验的 Studio 原生 ZIP，外加简洁报告：包类型与范围、校验结论、安装结论、E2E 结论、未验证项和风险。
- 仅保留用户明确要求的交付文件；不要因为本 Skill 删除历史 ZIP、工作区目录或用户文件。提交、推送和安装副本同步均需用户另行明确授权。
